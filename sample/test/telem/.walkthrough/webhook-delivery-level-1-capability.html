Webhook Delivery — What this flow does

When a Kafka message arrives on a topic, the platform looks up every registered subscriber for that topic and attempts to deliver the message to each one via HTTP POST. Every delivery attempt — success or failure — is written to the delivery log.

Pipeline

Kafka message Contains: topic, optional key, optional payload bytes.
→
Subscriber lookup Queries the database for all subscribers registered on the incoming topic. If none found, the message is silently committed with no side effects.
→
Flag check Each topic can have a delivery-blocked flag. If set, all subscribers are logged as "blocked" and no HTTP call is made.
→
HTTP fan-out One HTTP POST per subscriber, run in parallel. Each POST carries the raw payload and an idempotency key (X-Delivery-Id) that is stable across retries.
→
Delivery log Every attempt is written: subscriber ID, message key, payload, attempt number, status, HTTP status code, and error message.

Possible outcomes per subscriber

✓ Success — 2xx response → logged as "success", delivery complete.
◌ Blocked — topic flag is set → logged as "blocked", no HTTP call made.
↻ Retry — non-2xx or network error → logged as "failed", retried up to 6 times total.
✗ Exhausted — all 6 attempts failed → final attempt logged as "exhausted".

At-least-once guarantee

If the delivery log write fails (database error), the handler propagates the error so the Kafka offset is not committed. The message will be redelivered. This is intentional: a delivery attempt that cannot be recorded is treated as if it never happened.
