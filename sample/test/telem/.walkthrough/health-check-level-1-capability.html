Health Check — What This Feature Tests

Feature
Health check
3 scenarios  ·  GET /health

What the health check is

The health check is a single endpoint — GET /health — that always replies 200 { status: "ok" }. It has no business logic: it does not read from the database, check feature flags, or call any external service.

Its audience is orchestrators. Before sending production traffic to an instance, an orchestrator hits this endpoint. A 200 means "route here"; anything else means "wait or remove this instance from the pool."

What the test suite pins

Three properties of the endpoint are tested:

  1. Liveness. The service responds with 200 and a well-formed { status: "ok" } body when asked.
  2. Wire format. The response carries Content-Type: application/json so callers can safely parse it without special-casing.
  3. Read-only surface. Non-GET methods (e.g. POST) are not accepted — the endpoint cannot accidentally absorb mutation traffic if a misconfigured client targets the wrong path.
Not tested here

Dependency health (database reachability, Kafka lag, flagd connectivity) is not checked. This endpoint reports process liveness — whether the HTTP server is running — not system-wide health. Deep health probes are out of scope for this endpoint and these tests.

Glossary
Orchestrator
Automated system (Kubernetes, ECS, load balancer) that starts, stops, and routes traffic to service instances based on their reported health.
Liveness check
A minimal probe that answers "is the process alive and able to handle requests?" — distinct from a readiness check (can it serve this specific request?) or a dependency check (are its dependencies healthy?).
Wire format
The concrete encoding (here: JSON over HTTP) that callers must be able to parse without additional negotiation.
