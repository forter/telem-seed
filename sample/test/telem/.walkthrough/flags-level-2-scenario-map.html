GET reads4 scenarios
No delivery flags have been configured
GET returns 200 {} — an empty object, not an error. Topics absent from the flags file are simply absent from the response.
A blocked topic appears in the delivery flag listing
Pre-seeded: "orders" blocked. GET returns { "orders": true }. The flag entry's defaultVariant is 'on', which maps to true.
A topic with an explicit off flag appears as unblocked in the listing
Pre-seeded: "orders" with defaultVariant 'off'. GET returns { "orders": false }. The mapping is purely on the variant name, not the variant value — 'on' → true, anything else → false.
All blocked topics appear in the delivery flag listing
Two topics blocked ("orders", "payments"). GET returns both. Verifies iteration covers all entries, not just the first.
PATCH writes4 scenarios
Blocking a topic creates its delivery flag entry
PATCH { delivery_blocked: true } → 200 { topic: "orders", delivery_blocked: true }. Flags file gains the structured entry; both the response and the write are asserted.
Blocking an already-blocked topic is idempotent
Belt-and-suspenders. Topic already blocked; PATCH block again. The handler overwrites the entry unconditionally (no if-exists guard). Written file is identical to the primary blocking scenario.
Unblocking a topic removes its delivery flag entry
Topic pre-seeded as blocked. PATCH { delivery_blocked: false } → 200. Flags file entry is deleted; file becomes { flags: {} }.
Unblocking a topic that was never blocked is accepted
Belt-and-suspenders. No pre-seeding. PATCH unblock → 200. JS delete on an absent key is a no-op; the file write still happens with empty flags.

PATCH rejects non-boolean delivery_blocked values (6 types)
Scenario Outline. Inputs: absent, null, number, object, array, string — all produce 400 "delivery_blocked must be a boolean". No file IO runs; the handler returns before reading the flags file. Six rows because each is a distinct typeof outcome, even though all produce the same 400.
Infrastructure failures6 scenarios
GET returns 500 when the flags file is unavailable
File read throws (ENOENT-style). GET returns 500 "Internal server error".
PATCH returns 500 when the flags file is unavailable
File read throws. PATCH returns 500; no file write occurs.
GET returns 500 when the flags file is unavailable even with existing flag entries
Belt-and-suspenders. Topic pre-seeded + file made unavailable. Confirms the 500 path fires before flag iteration, regardless of prior state.
GET returns 500 when the flags file contains malformed JSON
File read succeeds; JSON.parse throws. Same 500 response, distinct failure mode.
PATCH returns 500 when the flags file contains malformed JSON
Same as above but on PATCH. No file write occurs.
GET/PATCH return 500 when malformed, even with existing entries
Belt-and-suspenders (2 scenarios). Confirms JSON parse fails before iterating or mutating flags, regardless of seeded state.
State consistency round-trips3 scenarios
GET reflects a topic that was just blocked
In a single scenario: PATCH block, then GET. Verifies the flags file state is visible to GET in the same process without a restart.
GET does not list a topic after it is unblocked
Pre-seeded blocked, then PATCH unblock, then GET → empty. Confirms the deletion takes effect immediately.
Unblocking one topic does not affect other blocked topics
Two topics seeded. Unblock one. GET shows only the remaining topic. Guards against the write accidentally clearing all flags.
Edge cases6 scenarios
Blocking a topic name containing hyphens is accepted
Topic: order-events. Hyphens are valid in Kafka topic names; the flag key must be stored verbatim.
Blocking a topic name with dots and underscores is accepted
Topic: order.events_v2. Dots and underscores are also valid.
PATCH with extra unknown fields in the body ignores them and succeeds
Body: { delivery_blocked: true, unknownField: "ignored", another: 42 } → 200. Extra fields are silently ignored.
Blocking "__proto__" creates no usable flag despite returning success ⚠
Latent bug. __proto__ is a legal Kafka topic name but a special JavaScript property key. The assignment hits the object prototype instead of creating an own key; the flags file remains empty. PATCH returns 200 but delivery is not blocked. Scenario pins the current (buggy) behavior.
Blocking "constructor" succeeds and creates a flag entry
Mirror of the __proto__ scenario. constructor is also a prototype property, but bracket-notation assignment creates an own key normally — it serializes and GET reports it. Documents the asymmetry.
GET reports blocked based on defaultVariant name, not variant value
Belt-and-suspenders. Pre-seeded: defaultVariant:'on' but variants:{on:false}. GET still returns true. The mapping is on the variant name only; the actual boolean value is never read. Untested coupling: PATCH always writes consistent entries, so this inconsistency only arises via manual file editing.
