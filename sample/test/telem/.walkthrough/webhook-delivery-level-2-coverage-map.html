Message with a matching subscriber is delivered successfully happy path
Given: 1 subscriber registered for topic "orders"
When: Kafka message on "orders" with key + payload
Then: HTTP POST made to subscriber URL with Content-Type, X-Delivery-Id, payload body
  & delivery log: status=success, http_status=200, attempt=1
Message without a key is delivered and logged with a null message key happy path
Same as above but message has no key → message_key: null in delivery log.
Message for a topic with no subscribers produces no side effects happy path
No subscriber exists for the topic → no HTTP call, no delivery log entry. The message is committed.
Blocked topic suppresses HTTP delivery and logs the subscriber as blocked flag
Topic-level kill-switch is set → no HTTP POST made; delivery log entry with status=blocked, http_status=null.
All subscribers for a blocked topic are each logged as blocked flag
2 subscribers, topic blocked → each gets its own blocked log entry; no HTTP calls.
DB failure during message processing prevents delivery and causes message retry infra failure
Database unavailable at subscriber lookup → handler throws → Kafka offset not committed → message replayed. No HTTP call, no delivery log.
DB write failure during delivery log recording prevents delivery and causes message retry infra failure
Subscriber lookup succeeds, blocked flag logged → delivery log INSERT fails → handler throws → Kafka replays. Tests the rejection-propagation path inside Promise.allSettled.
Persistent network errors exhaust all delivery retry attempts infra failure
Endpoint unreachable for all 6 attempts → delivery log: 5 × failed, 1 × exhausted; http_status=null; no HTTP call recorded (throws before recording).
HTTP 503 response exhausts all delivery retries infra failure
6 × HTTP 503 → delivery log: 5 × failed, 1 × exhausted; http_status=503; error_message="HTTP 503 Service Unavailable". All 6 HTTP calls are recorded.
HTTP 429 response exhausts all delivery retries infra failure
Same as 503 variant, http_status=429, error_message="HTTP 429 Too Many Requests".
HTTP 500 response exhausts all delivery retries infra failure
Same as 503 variant, http_status=500, error_message="HTTP 500 Internal Server Error".
Multiple subscribers for the same topic each receive an independent webhook delivery multi-subscriber
2 subscribers, same topic → 2 HTTP POSTs (parallel, each with its own X-Delivery-Id) → 2 success log entries.
One subscriber succeeds while another is unreachable in the same fan-out multi-subscriber
Subscriber 1 (reachable): 1 HTTP POST, 1 success log entry.
Subscriber 2 (unreachable): no recorded HTTP call, 6 network-error log entries (5 failed + 1 exhausted).
Message with a null value is delivered with an empty body and logged with an empty payload input shape
message.value = null → payload = "" → HTTP POST body is empty string; delivery log payload is "".
Message with neither key nor value is delivered and logged with null key and empty body input shape
Both null → message_key=null, payload="" in all outputs.
Empty-byte message key is delivered and logged with an empty-string key distinct from null input shape
message.key = empty buffer (truthy) → messageKey="" (not null). Delivery log: message_key="" ≠ null.
Subscriber custom headers are merged into the delivery call on top of the defaults input shape
Subscriber has custom headers (Authorization, X-Custom-Id) → HTTP POST headers include both defaults and custom headers (lowercased by the HTTP layer).
Endpoint returning HTTP 201 is treated as a successful delivery input shape
Any 2xx is success. http_status=201 in delivery log (not always 200).
Endpoint returning HTTP 204 is treated as a successful delivery input shape
http_status=204 in delivery log.
Delivery succeeds after a transient network failure on the first attempt input shape
Attempt 1 fails (network), attempt 2 succeeds. Delivery log: 1 "failed" + 1 "success". 1 HTTP call recorded (the successful one only).
Message with a Unicode payload is delivered and logged correctly input shape
Unicode (Japanese + emoji) survives intact through HTTP body and delivery log payload field.
Subscriber URL with query parameters is called with the full URL intact input shape
Query string (?env=prod&version=2) is not stripped from the URL in the HTTP POST.
SQL-special characters in the message payload are forwarded and logged without transformation input shape
Payload containing SQL injection chars ("; DROP TABLE …") is forwarded verbatim and stored literally in the delivery log. SQL safety is a parity-test concern, not here.
Message on one topic does not trigger delivery to subscribers of a different topic isolation
Subscriber 1 (topic=orders) receives the delivery. Subscriber 2 (topic=inventory) does not — no HTTP call, no log entry.
Blocking one topic does not suppress delivery on a different unblocked topic isolation
Topic "orders" is blocked. A message on topic "inventory" is delivered normally to its subscriber (subscriber 2). Subscriber 1 (orders) receives nothing.
