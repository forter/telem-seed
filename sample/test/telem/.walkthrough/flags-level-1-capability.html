Manage topic delivery flags

This feature covers the HTTP API for blocking and unblocking per-topic topic delivery. Two endpoints read and write a flags file that flagd watches.

Endpoints under test

GET /api/flags
Returns a map of every configured topic to its blocked status. Topics with no entry are absent from the response — they are not listed as false.
PATCH /api/flags/:topic
Sets or clears the delivery block for a single topic. { "delivery_blocked": true } creates an entry; false removes it. Body must be a boolean — any other type returns 400.

The flags file

Both endpoints operate on flags.json, a JSON file on the local filesystem. Blocking a topic adds a structured entry; unblocking deletes it. The file is the only IO boundary in this flow — no database, no Kafka, no outbound HTTP.

What is not covered here

Out of scope: the effect of a blocked flag on actual delivery. When a Kafka message arrives, the Kafka handler checks isTopicBlocked(), which reads the same file via flagd. That integration is tested in the Deliver webhooks to subscribers flow, not here. This feature tests only the HTTP responses and the flags file state.

Key facts from the feature file

GET returns {} when no flags have been configured — not an error.

Unblocking a topic that was never blocked is accepted (delete is a no-op, 200 returned).

Blocking __proto__ silently fails: PATCH returns 200 but the flag is never written. This is a documented latent bug.

The flags file path is captured at module load time; test isolation is handled by an in-memory fake that intercepts filesystem calls.
