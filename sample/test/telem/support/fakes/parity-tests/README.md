# Parity Test Ledger

Tracks parity coverage for every fake. Each fake is one of: **Covered**, **Not Covered** (with reason), or **Blocked** (with a `REQUIREMENTS.md` detailing what the owner team must supply).

Parity verifies **behaviour** — return values, error codes callers branch on, ordering, round-trip invariants, edge cases — by running the same operations against the fake and a real counterpart. It is never a shape check.

**One entry point:** `npm run bdd-test:fakes-parity` → `run.sh`. Never add per-fake scripts. A green `npm run bdd-test` says nothing about parity: the BDD suite never runs these specs.

| `non-determinism.ts` | **Not Covered** | No external real service to compare against. `crypto.randomUUID` and `setTimeout` are patched at the Node.js layer — their "real" behavior is Node.js built-in and well-specified. No fake storage semantics or external shape is hardcoded. The timer patch changes only the delay (to 0) and records the requested one; the callback, its arguments and the returned handle are passed through to the real `setTimeout`, so there is no behavior to re-derive. The one real difference — concurrent timers fire in registration order instead of shortest-delay-first — is a consequence of zeroing delays, documented in `non-determinism.ts`, and is not something a comparison against real timers could "fix". The recorded schedule is verified by the BDD retry scenarios and mutation-checked, not by parity. |

## Safety-net meta-tests

The ownership safety net itself (not a fake, but the harness's core mechanism) is verified by always-run scenarios in `test/telem/features/meta-tests.feature`. These are NOT parity tests — they don't compare a fake against a real service. They verify that unowned IO is caught and that cleanup isolates scenarios.

## Running

```bash
npm run bdd-test:fakes-parity      # starts MySQL and Kafka (Docker), runs every suite, tears them down
PARITY_MYSQL_PORT=3399 npm run …   # host port for the parity MySQL (default 3307)
PARITY_KAFKA_PORT=9399 npm run …   # host port for the parity Kafka (default 9392; the broker advertises this same port)
PARITY_COMPOSE_PROJECT=mine npm run …   # compose project name (default webhooks-parity) — set it to run two parity runs side by side
```

A single suite, with its container already up (`docker compose -p webhooks-parity -f test/telem/support/fakes/parity-tests/compose.parity.yaml up -d --wait [mysql|kafka]`):

```bash
npx tsx test/telem/support/fakes/parity-tests/fake-db.parity.ts
npx tsx test/telem/support/fakes/parity-tests/fake-kafka.parity.ts   # PARITY_KAFKA_PORT must match the running broker
```

Shared bootstrap for scenario context lives in `parity-setup.ts` — suites never set the scenario id themselves. Run each suite on its own at least once; a spec that only passes after a sibling set the id is broken.

## No CI — the local run is the gate

This sample app has no CI and won't get one (an accepted decision, not pending work). So `npm run bdd-test:fakes-parity` **on your machine, with Docker running,** is the only thing that exercises the SQL in `src/db/*` (BDD doesn't — the repositories are faked) and the Kafka driver against a real broker. Run it before pushing any change that touches `src/db/**`, `src/kafka/**`, `src/flags/**` or `test/telem/support/fakes/**`. A local skip ("Docker is not available") means parity did **not** run — start Docker and re-run rather than reading the skip as green. `CI=true npm run bdd-test:fakes-parity` makes a skip fatal if you want that guarantee locally.

`mysql:8` is a floating tag (8.4 at the time of writing) — pin it in `compose.parity.yaml` **and** the app's `docker-compose.yml` together if production pins a minor.
